# AGENTS.md — Dialog Survey Project Knowledge Base

> Updated: 2026-10-24 (v1.12.0). Sprint #153 (Conventional Commits + auto CHANGELOG + release automation). 77 source TS files (src/, excluding generated), 174 test files (162 + 12 e2e). Tests need no PostgreSQL (PGlite).

## Overview

AI-powered survey dialog bot — async multi-turn conversations via DingTalk with LLM-driven follow-ups and context memory. Fastify 5 + PostgreSQL + Prisma 7 (driver adapters) + custom LangGraph workflow.

## Conventions

| Rule | Detail |
|------|--------|
| **ESM imports** | Relative paths require `.js` extension |
| **Type imports** | `import type` for type-only, Biome `useImportType: error` |
| **No `forEach`** | Use `for...of`, Biome `noForEach: error` |
| **No console** | Use `logger.ts` (`info`, `error`, `warn`), Biome `noConsole: error` |
| **No explicit `any`** | Biome `noExplicitAny: warn` |
| **Return types** | Explicit on all public functions |
| **Error classes** | Custom subclasses (`StatePersistenceError`, `PlanNotFoundError`, etc.) |
| **Nunjucks filters** | Never chain filter after `or` — precedence trap |
| **HTMX auth** | Global via `htmx:configRequest` in `admin-tree.njk`, NEVER per-button `hx-headers` |
| **HTMX POST body** | `values: {}`, NEVER `body: JSON.stringify()` |
| **HTMX URLs** | Shell: `/admin/*`, Fragments: `/admin/content/*` |
| **Prisma client** | Import `PrismaClient` from facade `src/utils/prisma-client.js` (NEVER `src/generated/` directly); construct only via `createPrismaClient()` |

## Notes

- **No DB for tests**: full `vitest run` uses PGlite (WASM) per test file — no PostgreSQL required. DDL + data-dir caches live in `node_modules/.cache/dialog-survey/` (invalidated by schema hash); the first cold setup spawns `prisma migrate diff` (~2-4s). `globalSetup` auto-runs `prisma generate` once if `src/generated/prisma` is missing.
- **Test parallel safety**: suites run with `fileParallelism: true`; each file gets an isolated PGlite instance. On a gate failure, rerun the failing file in isolation first; fix cross-file collisions by scoping fixtures (file-unique ids, cleanup predicates) — never by weakening assertions.
- **Vitest async suites**: Vitest 4 awaits async `describe` callbacks — several suites rely on a describe-level `await getSharedTestPrisma()`. Re-verify async-suite semantics when upgrading Vitest.
- **Process pollution**: `tsx --watch` leaves orphan processes. Styling issues → find the PID (`netstat -ano | findstr :3001` on Windows, `fuser -k 3001/tcp` on WSL/Linux) and kill it first.
- **Test layers**: Unit (mock Prisma) / Integration (PGlite in-process, parallel-safe) / E2E in `tests/e2e/` (12 files: in-process Fastify + real chromium via Playwright).
- **CI**: PRs run 12 jobs (static-analysis, unit-tests, integration-tests, backup-drill, security-scan, coverage, e2e-tests, mutation-tests [advisory], smoke, commit-lint, version-consistency, lockfile-registry). No PostgreSQL service; the consuming jobs run `npx prisma generate` before tsc/vitest (security-scan, version-consistency and lockfile-registry are static-only; generated client is gitignored). **Integration suites must be named `*.integration.test.ts` (dot, not hyphen)** — the job glob is `tests/*.integration.test.ts` and the unit job excludes the same pattern, so a hyphenated name is silently selected by the wrong job.
- **Mutation testing (issue #155)**: Stryker + vitest runner via `stryker.conf.json`. Incremental runs (`scripts/mutation-test.mjs`) mutate only files changed vs the base ref and fan out over ≥4 workers; the CI `mutation-tests` job is advisory (`continue-on-error`). Mutant runs use `vitest.config.mutation.ts` (e2e excluded, no retries). **`ignorePatterns` entries must be anchored with a leading `/`** — Stryker matches them anywhere in the tree, so a bare `reports` also excluded `src/views/reports/`, the sandbox lost those `.njk` templates, and *every* mutant run died in its dry run with `GET /admin/reports` → 500 (the view engine could not find `reports/index.njk`). That surfaced as `✗ Gate M BLOCK … mutation score 0.0%` on every push touching `admin-templates.ts`. If Gate M reports 0.0% with "no test file found" warnings, check `ignorePatterns` anchoring before suspecting the tests.
- **Gate M threshold is 60%, and this codebase sits near it.** Measured scores: `stream-message.service.ts` 62.69%, `admin-templates.ts` 61.22% (both 61.20% in one run). Gate M only mutates files changed against the base ref, so a push that touches nothing in `src/` never runs it — which is why the gap went unnoticed for a long time. Do not "fix" a Gate M block by writing a `.mutation-baseline.json` by hand: a baseline can only *raise* the effective threshold (`Math.max(threshold, baselineScore)`), so a fabricated one makes the gate stricter, not looser. Raise the score with tests, or set an honest per-file threshold with an `@mutation-threshold: N` comment in the corresponding test file (`detect-ai-test.ts` reads it).
- **Gate M needs four local patches to work at all — and xp-gate updates erase them.** The gate lives outside this repo (`~/.config/xp-gate/`). Three upstream bugs in `modules/mutation/runners/stryker-runner.ts` and one in `hooks/pre-push` make it report 0.0% or SKIP regardless of test quality: repeated `--mutate` keeps only the last file, `--config` is not a Stryker option, the report is schema 1.0 (raw mutants, no aggregate score), and the TypeScript hook branch never passes `--timeout` so it uses a 120s default while these two files need ~48 minutes. Run `node scripts/verify-xp-gate-patches.cjs` to check, `--fix` to restore the hook timeout. **A blank "mutation score 0.0%" is a patch problem, not a test problem** — check this before writing more tests. Issue #209 tracks it.
- **The mutation threshold is also enforced by this repo, not only by the patched gate.** `stryker.conf.json` sets `break: 0`, so Stryker itself never fails on a low score; the 60% verdict used to come exclusively from the patched xp-gate runner. `scripts/mutation-test.mjs` now reads `.stryker-report.json` and aggregates the schema-1.0 mutant list itself, exiting 1 below the threshold (override with `MUTATION_THRESHOLD`). It exits 2 when the report is missing or has no scored mutants — "no evidence" is never a pass. `npm run test:mutation:verify` re-judges an existing report without re-running Stryker. So the threshold gives an honest verdict even with the global patches gone.
- **What a surviving mutant usually means here**: an unassertable side effect. Mocking `../src/utils/logger.js` and asserting the message turned a whole cluster of "retries exhausted" survivors into kills — the branch ran, nothing observable changed. Same for error paths: assert the exact response body, not just the status code.
- **xp-gate Gate 6 `DeadSymbol` false positives (verified on xp-gate 0.30.5)**: archlint reports `InterviewPlanSendService.{sendInvitations,resendToInterview,pausePlan,resumePlan,cancelPlan}` and `InterviewPlanService.importMembers` as dead. **They are not** — all are called from `src/api/plans.ts`, passed either to `registerLifecyclePost(path, (id) => planService.X(id))` or as a direct `planService.X(...)` call inside a route handler. archlint resolves direct calls but not a method reached through a callback/function reference, so a method that is only ever invoked indirectly looks unreferenced. Before "fixing" any DeadSymbol finding on this codebase, `grep` the method name across `src/` plus `tests/` — the ratchet baseline (`.architecture-baseline.json`) records them as known, so they do not block. Do not delete these methods and do not add `# noqa`-style suppression; the false positive is a tool limitation, not a code smell.
- **API bug triage**: curl → isolate backend first. htmx.ajax() `.then()` fires on 4xx with `undefined` arg.
- **Credential-free startup (issue #171)**: without `DINGTALK_CLIENT_ID`/`DINGTALK_CLIENT_SECRET`, `buildApp()` boots read-only (no Stream client). `runPostListenStartup` resends unsent messages only when all three DingTalk creds are set and `DISABLE_STARTUP_RESEND` (1/true/yes) is not set — startup outbound sends are a production side effect, never re-enable them unconditionally.
- **The gates run natively in Git Bash; `scripts/run-xp-gate-native.sh` is the entry point.** Every gate problem on this machine traced back to one line of environment: `bash` on the Windows PATH resolved to `C:\WINDOWS\system32\bash.exe`, which is the **WSL launcher**, not Git Bash. `core.hooksPath` points at a `#!/bin/bash` hook, so a `git commit` from Windows silently ran the whole suite inside WSL — a different filesystem, a different Python, and a different user's `~/.local/bin`. A `scripts/run-xp-gate.sh` wrapper used to exist to survive that jump (mount-translating `node` shims, `.exe` shims, a Windows `HOME`, `PYTHONUSERBASE`); it was deleted once PATH was fixed, because every workaround in it was compensating for a cross-environment hop nothing had asked to cross. Every tool the gates need is installed **natively on Windows** — node, git, gitleaks (scoop shim), `lizard` (`~/.local/bin`), `semgrep` (`~/bin`), `detect-secrets-hook` (`%APPDATA%\Python\Python312\Scripts`) — so with PATH ordered correctly (next bullet) the hooks run in Git Bash directly: one filesystem, one PATH, one Python, zero `/mnt/` paths. `scripts/run-xp-gate-native.sh` runs them explicitly and prints the resolved path of every tool first, so a wrong interpreter is visible in the first six lines instead of surfacing later as a mystery SKIP; `scripts/run-xp-gate-native.ps1` is the same from a PowerShell prompt. Measured: 10.0/10 effective with 9/12 gates actually executing (Gate 6 PASS, Gate 8 a real PASS from both scanners, Gate 10 PASS).
- **Development happens on Windows only; WSL is for running and deploying, not developing.** The project targets Linux in production (`DEPLOY.md`: any Linux box with Node 20.19+ and PostgreSQL 14+; Windows/macOS are dev-only), but nothing in this repo's development flow requires WSL — `scripts/deploy.sh`, the `Dockerfile`, `docker-compose.yml` and every CI workflow are WSL-agnostic, and the gates run entirely on Windows. A WSL worktree was tried and removed: it worked (167/167 files, 1967 tests, `tsc` clean, `biome check` clean on 284 files, 8/12 gates), but it duplicated a 663 MB dependency tree and needed manual syncing for an environment that gets little use. If someone does need to run the gates in WSL, they must use a checkout on the **Linux filesystem**, never `/mnt/*`: `/mnt/d` is one directory seen by two operating systems, so it carries a single `node_modules` holding only the native binaries of whichever platform last ran `npm install` — Windows writes `@biomejs/cli-win32-x64`, WSL needs `cli-linux-x64`, and Gate 1 then dies with `Cannot find module '@biomejs/cli-linux-x64/biome'` under `BLOCKED - Biome check failed`, which reads as a lint problem. Two further traps for that case: `~/.local/bin` (where the pip/tarball gate tools live) is added only by `~/.profile`, which non-interactive shells do not read, and the shared `core.git/config` `core.hooksPath` points at `C:/Users/think/.config/xp-gate/hooks` — a Windows path that does not exist in WSL, so a `git commit` there succeeds while silently skipping every gate.
- **PATH is ordered so `git commit` reaches Git Bash, and that ordering is load-bearing.** Windows concatenates the **machine** PATH row before the user row, so a user-PATH entry cannot outrank a machine entry — adding `C:\Program Files\Git\bin` to the user PATH did nothing while `C:\WINDOWS\system32` sat at machine index 5. `C:\Program Files\Git\bin` is therefore prepended to the **machine** PATH (index 0, ahead of `system32`), which is what makes a plain `git commit` run the hooks in Git Bash instead of the WSL launcher. Setting it needs admin rights (`Start-Process powershell -Verb RunAs`). Verify the ordering actually took effect by reading the registry, not `$env:PATH` — a running shell keeps the environment it was started with, so every child process inherits the *old* value and `where bash` keeps reporting `System32` until the shell is restarted:
  ```powershell
  (Get-Item 'HKLM:\SYSTEM\CurrentControlSet\Control\Session Manager\Environment').GetValue('Path', $null, 'DoNotExpandEnvironmentNames') -split ';' | Select-Object -First 3
  ```
  Do not "fix" the problem by deleting `system32\bash.exe` — `wsl` itself lives there, and `wsl` must keep working.
- **"Gate tool not installed" almost never means it is not installed.** `lizard` (Gate 3), `semgrep` (Gate 10) and `detect-secrets-hook` (Gate 8) are pip installs; they land in a *user* script directory, and two separate things hid them. First, the profile files that add that directory are read only by *interactive login* shells, so `command -v` in a non-interactive gate shell found nothing. Second — and this survives fixing the first — Python resolves user site-packages from `$HOME`, so under the old WSL wrapper, which repointed `HOME` at the Windows profile, a console script on PATH died with `ModuleNotFoundError: No module named 'semgrep'`. Both are handled now without any of that machinery: `scripts/run-xp-gate-native.sh` adds `~/.local/bin`, `~/bin` and the Windows Python `Scripts` dir to PATH, and Git Bash's `$HOME` already is the Windows profile, so `PYTHONUSERBASE` is unnecessary. Check the tool's own directory before installing anything — the versions natively installed here were in fact *newer* than the WSL ones.
- **Gate 5's local coverage judgement was inert (xp-gate #594), worked around in `vitest.config.ts`.** Gate 5 runs `vitest run --coverage <changed test files>`; when none of those tests imports a src module, istanbul writes `total.lines.pct = "Unknown"`, the hook does `Math.round("Unknown")` → `NaN`, and `[ NaN -lt 80 ]` makes bash print `integer expression expected` and return **2** — which `if` reads as "condition false", so it took the PASS branch and logged `NaN% ✅`. `coverage.include: ['src/**/*.ts']` + `cleanOnRerun: false` forces untested files into the report on a subset run too, so the total is always a real number. Verify with `tests/coverage-gate.test.ts`. Full-suite coverage is ~93.9% lines and unchanged by this. Do not re-add `coverage.all` — it no longer exists in `@vitest/coverage-v8` v4 and silently does nothing.
- **The full-history secret scan is a real gate again, via a fingerprint baseline (issue #211).** `scripts/scan-git-history-secrets.mjs` scans every commit (the `gitleaks-action` step only scans PR diffs, which is how two provider keys and a DingTalk app secret sat unreported for months). The CI step used to be `continue-on-error: true` so eleven known historical findings would not keep it permanently red — which also meant a NEW leak could never fail the build. `.secrets-history-baseline.json` now names each known finding by **fingerprint = sha256(rule + NUL + file + NUL + line), first 16 hex chars**, with a hand-written reason, and anything outside that list exits 1. Three rules keep the baseline from becoming the vulnerability it guards against: **(1)** an entry that matches nothing is itself a failure, so the file cannot rot into a wildcard; **(2)** matching is on rule+file+line, not file, so a new secret on another line of a historical file still fails; **(3)** the secret text is never stored — a baseline embedding the plaintext would be a second copy of the leak in a public repo. Regenerate only with `--write-baseline` **after** reading every finding; entries it cannot attribute are marked `NOT REVIEWED` and a test fails on that marker. The historical entries cannot be removed by rewriting history (pushed and cloned); they are acceptable because the DingTalk credentials belong to a virtual/test organization and both cloud keys are revoked.
- **A clean verdict from a scan that read nothing is the worst outcome, and there are now three guards against it.** `scan-git-history-secrets.mjs` exits 2 — never 0 — when gitleaks is missing, when `.gitleaks.toml` is absent, and when `git rev-list --all --count` is 0. The last one is not hypothetical: `gitleaks git` in a directory that is not a repository exits 0 with an empty report, so without the commit-count check the guard announced "history is clean" for a history it had never read. Same class of mistake as treating a missing scanner as a pass.

- **Gate 8 needs two things that look like one.** `adapters/gate-8.sh` gates the detect-secrets half on `command -v detect-secrets-hook && [ -f .secrets.baseline ]`, so with the tool present but no baseline it still prints "unavailable". `.secrets.baseline` is committed and `.gitleaks.toml` allowlists it — the baseline contains every pattern it found as literal text, which made gitleaks report 158 hits in it. `detect-secrets-hook` also rewrites line numbers in the baseline, so a Gate 8 block reading "Please `git add .secrets.baseline`" just means re-stage that file.
- **Gate 8 reports SKIP, not PASS, and that is correct behaviour for a broken check.** gitleaks 8.30.1 does not create its `--report-path` file when a scan finds nothing, and the gate decides "did the scan run?" from that file — so on any clean machine it prints `gitleaks exited 0 but produced no readable report` and reports SKIP. The scan *does* run (`INF scanned ~N bytes` / `INF no leaks found`); the gate simply has no evidence it can trust. xp-gate #592. Do not "fix" this by making the gate print PASS, and do not treat Gate 8 SKIP as a scan failure.
- **`bash -n` both hooks before trusting any gate result.** An xp-gate self-update on 2026-10-24 introduced a stray backtick in `hooks/pre-commit` (`echo "... $new_file — ..."`), bash read the closing backtick as a command substitution start, and the file stopped parsing — so every gate after Gate 5 silently did not run while the commit was let through. `scripts/verify-xp-gate-patches.cjs` now runs `bash -n` over `pre-commit` and `pre-push` and fails if either does not parse; `npm run smoke` calls it. A syntax error is fatal to *all* gates, so it is reported separately from the Gate M patch verdict.
- **Commits**: Conventional Commits are enforced in CI by the `commit-lint` job (PR title blocking; branch range advisory). An opt-in local hook exists but is **not installed by default** — run `scripts/install-git-hooks.sh install` to enable it. See `docs/contributing.md`.
- **Releasing**: `scripts/release.sh` is a **dry run by default**; pass `--execute` to release. It refuses to start unless `VERSION == package.json`, requires `GITHUB_TOKEN` when `github.release=true` (release-it otherwise skips the GitHub Release and still exits 0), and verifies the result afterwards. The `after:bump` hook key in `.release-it.json` must be the **bare** `after:bump`: a key naming a plugin namespace (e.g. `after:version:bump`) is never invoked, which leaves `VERSION` and `AGENTS.md` stale while still exiting 0 and still tagging. `tests/release-hook-key.test.ts` is the behavioural control proving this. Never force-move a released tag.
- **The container deployment is now guarded by tests, and five of its defaults are load-bearing (issues #212–#218).** `tests/docker-compose-deployment.test.ts` (structure), `tests/docker-engine-consistency.test.ts` (Node version), `tests/lockfile-registry.test.ts` (lockfile hosts) and `tests/health-readiness.test.ts` (route semantics) fail if any of these is undone, so they read as constraints on every future change: **(1)** `package-lock.json` may only resolve from `registry.npmjs.org`/`yarnpkg.com` — `npm ci` fetches exactly the recorded URLs and `--registry` cannot override them for lockfileVersion 3, and `npm ci --package-lock-only` will NOT rewrite hosts on an otherwise-current lock (it prints "up to date" and exits 0), so a host fix is an explicit edit, not a regenerate. `.npmrc` selects the official registry; mirror acceleration is a per-machine setting. **(2)** `/health` is a LIVENESS probe (200 for `degraded`, 503 only when the DB is down) and `/health/ready` is the READINESS probe (200 only when everything works). Anything that waits for a working deployment — compose healthcheck, Dockerfile `HEALTHCHECK`, orchestrators — must poll `/health/ready`; both also parse the body, because `r.ok` alone made a deployment with no LLM key report `healthy` (#218). `start_period` is 60s because the first readiness probe awaits the 30s LLM timeout. **(3)** In `docker compose`, every `$` in a bcrypt hash must be written `$$` — `env_file` values are interpolated, so `$2b$12$…` reaches the container as `$2b$12` and the admin login 401s forever (measured). `docker run -e` does NOT interpolate, so the two paths need different literals from the same hash. `admin-auth.ts` now answers a malformed hash with 500 + an explicit message rather than a 401. **(4)** `POSTGRES_PASSWORD` is required via `${POSTGRES_PASSWORD:?…}` (no `change-me-in-env` default) and the postgres port is NOT published — the app uses `postgres:5432` internally, and a host mapping both collides with a local PostgreSQL and exposes the DB to the LAN (#215). **(5)** `REPORTS_DIR=/app/reports` is backed by the `reports_data` named volume; a bind mount hits the uid 1000-vs-1001 `nodejs` ownership trap, so the volume is the supported shape, and a backup covers **two** volumes (#216).
- **The CJK font is a Git LFS object, and the build now refuses to ship a pointer (#217).** `assets/fonts/*.otf` is LFS-tracked, so a clone without `git lfs pull` — CI without `lfs: true`, `git archive`, any scripted checkout — contains a 133-byte pointer that passes every "does the font exist" check. `scripts/verify-font-asset.mjs` validates the BYTES (LFS magic, OpenType/TrueType magic, size floor) in both Dockerfile stages; keep that RUN in the runner stage too, because that is the stage whose bytes actually ship. A missing font is logged at `error` (not `warn`) in `ExportService` — every exported PDF loses its Chinese text. If PDF export looks fine but Chinese is blank, check `git lfs ls-files` before touching the template.
- **Node 22 is the floor, enforced in three places that must agree.** `Dockerfile` (`FROM node:22-slim` in both stages), `package.json` `engines`, and `.nvmrc` all say 22, because `@fastify/secure-session` → `@fastify/cookie` → `cookie@2` declares `engines.node: >=22`. `package.json` overrides `@fastify/cookie` to `11.1.0` — the last release on `cookie@1` — which deduplicates `cookie` to a single `>=18` entry; dropping that override reintroduces the EBADENGINE warning and the engine test fails on `node_modules/@fastify/cookie/node_modules/cookie`. Bumping the image (not downgrading the dependency) was the honest fix: the code already ran on a runtime it declared unsupported. `tests/docker-engine-consistency.test.ts` parses all three plus every lockfile `engines.node`, handling `||` alternatives (`>=23.5.0 || ^22.13.0 || ^20.17.0`, as @inquirer publishes) rather than naively reading the first integer.
- **The Docker image prunes build-time tooling, so it has no Prisma CLI (issue #210).** `Dockerfile` runs `scripts/prune-runtime-deps.mjs` between `npm run build` and the runner stage: `node_modules` 731 MB → 163 MB, image 1.22 GB → 574 MB. `npm prune --omit=dev` cannot do this — `prisma` and `typescript` are devDependencies AND optional peerDependencies of `@prisma/client`, so npm keeps them as `devOptional` and drags in Prisma Studio, `effect` and an embedded PGlite. Two consequences to remember: **(1)** `CMD` no longer calls `node node_modules/prisma/build/index.js migrate deploy` — that path is gone — it calls `scripts/migrate-deploy.mjs`, which applies `prisma/migrations/*.sql` with `pg` and writes `_prisma_migrations` in Prisma's own format (same SHA-256 checksums), verified in both directions against the CLI, so `deploy.sh`'s `prisma migrate deploy` and the container stay interchangeable. **(2)** The base image is **Debian slim, not Alpine**: `sodium-native` (via `@fastify/secure-session`) has no `linux-x64-musl` prebuild, so an Alpine image dies at boot with `Cannot find addon '.' imported from sodium-native/binding.js`. This was true of the Alpine Dockerfile *before* pruning too — the image had simply never been run. **`SESSION_SALT` is 32 hex characters** (`Buffer.from(salt, 'hex')` + secure-session's 16-byte requirement); 16 arbitrary characters fails with the misleading `salt must be length 16`. And `pino-pretty` is a devDependency, so `createLoggerConfig` falls back to plain JSON when it is absent — otherwise a container started without `NODE_ENV=production` crashed at boot.
