# AGENTS.md — Dialog Survey Project Knowledge Base

> Updated: 2026-11-07 (v1.18.0). 79 source TS files (src/, excluding generated), 192 test files (180 + 12 e2e), 2435 passing tests. Tests need no PostgreSQL (PGlite).

## Overview

AI-powered survey dialog bot — async multi-turn conversations via DingTalk with LLM-driven follow-ups and context memory. Fastify 5 + PostgreSQL + Prisma 7 (driver adapters) + custom LangGraph workflow.

## Conventions

| Rule | Detail |
|------|--------|
| **ESM imports** | Relative paths require `.js` extension |
| **Type imports** | `import type` for type-only, Biome `useImportType: error` |
| **No `forEach`** | Use `for...of`, Biome `noForEach: error` |
| **No console** | Use `logger.ts` (`info`, `error`, `warn`), Biome `noConsole: error` |
| **No explicit `any`** | Biome `noExplicitAny: warn` |
| **Return types** | Explicit on all public functions |
| **Error classes** | Custom subclasses (`StatePersistenceError`, `PlanNotFoundError`, etc.) |
| **Nunjucks filters** | Never chain filter after `or` — precedence trap |
| **HTMX auth** | Global via `htmx:configRequest` in `admin-tree.njk`, NEVER per-button `hx-headers` |
| **HTMX POST body** | `values: {}`, NEVER `body: JSON.stringify()` |
| **HTMX URLs** | Shell: `/admin/*`, Fragments: `/admin/content/*` |
| **Prisma client** | Import `PrismaClient` from facade `src/utils/prisma-client.js` (NEVER `src/generated/` directly); construct only via `createPrismaClient()` |

## Anti-Patterns (This Project)

| Pattern | Severity | Detail |
|---------|----------|--------|
| `new PrismaClient()` outside `prisma-factory.ts` | ERROR | Construct via `createPrismaClient()`; services receive `prisma` via DI |
| `prisma.$MODEL.$METHOD()` in API layer | ERROR | Route through repositories |
| Public `prisma` getter on services | ERROR | Encapsulate with discriminated unions |

## Notes

- **No DB for tests**: full `vitest run` uses PGlite (WASM) per test file — no PostgreSQL required. DDL + data-dir caches live in `node_modules/.cache/dialog-survey/` (invalidated by schema hash); the first cold setup spawns `prisma migrate diff` (~2-4s). `globalSetup` auto-runs `prisma generate` once if `src/generated/prisma` is missing.
- **Test parallel safety**: suites run with `fileParallelism: true`; each file gets an isolated PGlite instance. On a gate failure, rerun the failing file in isolation first; fix cross-file collisions by scoping fixtures (file-unique ids, cleanup predicates) — never by weakening assertions.
- **Vitest async suites**: Vitest 4 awaits async `describe` callbacks — several suites rely on a describe-level `await getSharedTestPrisma()`. Re-verify async-suite semantics when upgrading Vitest.
- **Process pollution**: `tsx --watch` leaves orphan processes. Styling issues → find the PID (`netstat -ano | findstr :3001` on Windows, `fuser -k 3001/tcp` on WSL/Linux) and kill it first.
- **Test layers**: Unit (mock Prisma) / Integration (PGlite in-process, parallel-safe) / E2E in `tests/e2e/` (12 files: in-process Fastify + real chromium via Playwright).
- **CI**: PRs run 12 jobs (static-analysis, unit-tests, integration-tests, backup-drill, security-scan, coverage, e2e-tests, mutation-tests [advisory], smoke, commit-lint, version-consistency, lockfile-registry). No PostgreSQL service; the consuming jobs run `npx prisma generate` before tsc/vitest (security-scan, version-consistency and lockfile-registry are static-only; generated client is gitignored). **Integration suites must be named `*.integration.test.ts` (dot, not hyphen)** — the job glob is `tests/*.integration.test.ts` and the unit job excludes the same pattern, so a hyphenated name is silently selected by the wrong job.
- **Mutation testing (issue #155)**: Stryker + vitest runner via `stryker.conf.json`. Incremental runs (`scripts/mutation-test.mjs`) mutate only files changed vs the base ref and fan out over ≥4 workers; the CI `mutation-tests` job is advisory (`continue-on-error`). Mutant runs use `vitest.config.mutation.ts` (e2e excluded, no retries). **`ignorePatterns` entries must be anchored with a leading `/`** — Stryker matches them anywhere in the tree, so a bare `reports` also excluded `src/views/reports/`, the sandbox lost those `.njk` templates, and *every* mutant run died in its dry run with `GET /admin/reports` → 500 (the view engine could not find `reports/index.njk`). That surfaced as `✗ Gate M BLOCK … mutation score 0.0%` on every push touching `admin-templates.ts`. If Gate M reports 0.0% with "no test file found" warnings, check `ignorePatterns` anchoring before suspecting the tests.
- **Gate M threshold is 60%, and this codebase sits near it.** Measured scores: `stream-message.service.ts` 62.69%, `admin-templates.ts` 61.22% (both 61.20% in one run), and `stream-message-utils.ts` **79.83%** (95/119 scored, measured 2026-11-03 with `node scripts/mutation-test.mjs --files src/services/stream-message-utils.ts`). Gate M only mutates files changed against the base ref, so a push that touches nothing in `src/` never runs it — which is why the gap went unnoticed for a long time. Do not "fix" a Gate M block by writing a `.mutation-baseline.json` by hand: a baseline can only *raise* the effective threshold (`Math.max(threshold, baselineScore)`), so a fabricated one makes the gate stricter, not looser. Raise the score with tests, or set an honest per-file threshold with an `@mutation-threshold: N` comment in the corresponding test file (`detect-ai-test.ts` reads it).
- **Some survivors are provably equivalent mutants — prove it before writing tests for them.** After raising `stream-message-utils.ts` to 79.83%, 20 survivors remained. One is worth recording because it looks killable and is not: `readField`'s guard (`!container || typeof container !== 'object'`) mutated at column 21 only turns `typeof container !== 'object'` into `false`, leaving `!container ||`. For `null`/`undefined`/`''`/`0`/`false`/arrays/objects the two versions are identical, and for strings and numbers the only way they differ is a key that is a real property — `'abc'['length']` is `3`. The function is only ever called with the keys `content`, `richText`, `text` and `markdown`, none of which exist on a string or a number, so **no test can ever kill it**. Verified by enumerating the real key set: 0 behavioural differences. The statement-level mutant at column 7 *is* killable and already is. Writing a test that merely "covers" an equivalent mutant produces a green delta with no protection — classify the survivor first.
- **Gate M needs four local patches to work at all — and xp-gate updates erase them.** The gate lives outside this repo (`~/.config/xp-gate/`). Three upstream bugs in `modules/mutation/runners/stryker-runner.ts` and one in `hooks/pre-push` make it report 0.0% or SKIP regardless of test quality: repeated `--mutate` keeps only the last file, `--config` is not a Stryker option, the report is schema 1.0 (raw mutants, no aggregate score), and the TypeScript hook branch never passes `--timeout` so it uses a 120s default while these two files need ~48 minutes. Run `node scripts/verify-xp-gate-patches.cjs` to check, `--fix` to restore the hook timeout. **A blank "mutation score 0.0%" is a patch problem, not a test problem** — check this before writing more tests. Issue #209 tracks it.
- **The mutation threshold is also enforced by this repo, not only by the patched gate.** `stryker.conf.json` sets `break: 0`, so Stryker itself never fails on a low score; the 60% verdict used to come exclusively from the patched xp-gate runner. `scripts/mutation-test.mjs` now reads `.stryker-report.json` and aggregates the schema-1.0 mutant list itself, exiting 1 below the threshold (override with `MUTATION_THRESHOLD`). It exits 2 when the report is missing or has no scored mutants — "no evidence" is never a pass. `npm run test:mutation:verify` re-judges an existing report without re-running Stryker. So the threshold gives an honest verdict even with the global patches gone.
- **What a surviving mutant usually means here**: an unassertable side effect. Mocking `../src/utils/logger.js` and asserting the message turned a whole cluster of "retries exhausted" survivors into kills — the branch ran, nothing observable changed. Same for error paths: assert the exact response body, not just the status code.
- **`.archlint.yaml` scopes Gate 6, and its `ignore` key REPLACES the default list.** `archlint init` writes a default that includes `**/tests/**` and friends; a config file that omits them does not extend the defaults, it discards them. Measured 2026-11-03: no config 142 smells (grade 5.4/10), config missing the defaults **194** smells (grade 4.2/10, 138 of them with a `tests/` primary file — 72 CodeClone plus 41 DeadSymbol against test doubles like `FakeWebSocket.send`), config as committed **72** smells (grade **7.1/10**, Fair). The committed file therefore restates the defaults explicitly and adds the genuinely foreign paths: `**/*.min.js` and `public/js/**` (51 findings, from `htmx.min.js`/`alpine.min.js` — a minified bundle is *supposed* to have CCN 116), `.sprint-history/**`, `docs/sprints/**` (archived one-shot scripts), `.git/**` (agent tooling), `tools/spike/**`. `tests/archlint-scope.test.ts` guards all of it. Note archlint reports Windows extended-length paths (`\\?\D:\...`), so normalise before matching file prefixes.
- **Gate 7 (`IaC security`) never ran until 2026-11-03 because it only scans *changed* files.** `adapters/gate-7.sh` prints "No IaC files detected in changes" and PASSes, so a repo whose `Dockerfile` is never edited in a given commit is never scanned. Run it deliberately: `checkov -d . --framework dockerfile` (162 checks), `checkov -d .github/workflows --framework github_actions`, and `hadolint Dockerfile`. The first real run found **3 genuine failures** — `pr.yml`, `loadtest.yml`, `publish.yml` and `spike-prisma7.yml` were missing a **top-level** `permissions:` block (job-level ones do not satisfy CKV2_GHA_1, because an unlisted future job still inherits the repo default, historically `write-all`). All four now declare one. `spike-prisma7.yml` had no permissions block at all. hadolint's five findings are deliberate and recorded in `.hadolint.yaml` with per-rule reasoning: `DL3025` (the HEALTHCHECK shell form is asserted by `tests/docker-compose-deployment.test.ts`), `DL3059` (the RUNs sit on opposite sides of the `prune-runtime-deps.mjs` step, #210), `DL3066` (`USER nodejs` matches the fixed uid 1001 that the reports volume ownership depends on, #216). **Suppressing a linter finding is only acceptable when the config file says why** — that is what keeps `.hadolint.yaml` from becoming a silencer.
- **Gate 6 `DeadSymbol` reports methods reached only indirectly; the suppression that actually works is a bare `// archlint-disable-next-line`.** archlint resolves direct calls but not a method invoked through a callback or function reference, so `InterviewPlanServiceBase.{createPlan,getPlan,listPlans,findByIdWithTemplate,…}` (10 methods, all reached from `src/api/plans.ts` through `registerLifecyclePost(path, (id) => svc.X(id))`) and `InterviewPlanService.{addMember,removeMember,sendReminder,importMembers}` looked unreferenced — 22 false positives in this repo. Each now carries `// archlint-disable-next-line` on the line directly above the method. **Three mechanics, each verified against a fixture:** (1) the directive must be the WHOLE comment — `// archlint-disable-next-line — because …` does NOT suppress, and the trailing explanation silently kills it, so any reasoning has to live on its own line above; (2) naming a rule after the directive (`…-next-line dead_symbol`) also does NOT suppress; (3) it works on class methods and `async` methods, and covers exactly the one following line. Two config-level alternatives do NOT work on archlint 0.16.0: `excludeSymbols` is accepted and ignored (a `foo` symbol stayed reported), and `entry_points` — which archlint's own `dead_code` explanation recommends — is likewise silently ignored. **`ignore` is the only config key that suppresses anything**, and for `dead_code` (whole-file) it is the only lever, because a file-level `// archlint-disable-next-line` does nothing. Before suppressing, `grep` the name across `src/` AND `tests/` — one of the 23 was genuinely dead (`DingTalkClient.generateSignature`, an exact duplicate of `middleware.ts#generateSignature` that nothing called) and was deleted instead.
- **archlint's `VendorCoupling` counts this repo's own `src/core/types/index.ts` as a third-party package (14 of 14 internal hits were false).** The detector flags any module imported by "many" files and cannot tell an internal barrel from node_modules, so `src/core/types/index.ts` (14 files) reports alongside genuine externals — `fastify` 52 files, `vitest` 184, `@fastify/secure-session` 17, `nunjucks` 14, `@fastify/csrf-protection` 14, `@fastify/view` 11, `playwright` 11. The external half is normal framework usage, not a defect. Do not chase these; they are most of the reason `-A` (all detectors) reports 172 smells against the default 72.
- **Gate 3 measures only cyclomatic complexity, and nothing in this pipeline measures cognitive complexity.** `adapters/gate-3.sh` shells out to lizard and never asks for the cognitive metric. **lizard has supported it since 1.24.1** (`-Ecognitive`, a `CogC` column, `--CogC N` defaulting to 15) — but this machine was pinned at 1.21.3, which predates the feature, so `lizard --help` showed nothing and an earlier reading of this file concluded the metric did not exist. It does; it is simply not requested. archlint *does* compute `high_cognitive_complexity` and enables that detector by default, but Gate 6 runs archlint without `-A` and only compares against the snapshot baseline, so the number is computed and then discarded. Measured consequence: `scripts/cli.mjs#installCommand` reached cognitive **56** / cyclomatic **36** while every gate reported green — it IS in Gate 3's scan scope (the `CC_FILES` regex includes `.js`) but `.ccn-baseline.json` covers 61 `src/` files and **zero** `scripts/` files, so it had never been graded. Refactored here into 5 step functions; `statusCommand` (23) split into two platform reporters; `resolveInstallConfig` (16) reduced to a dispatch table over 4 helpers. Two things to keep in mind: decomposing a function does NOT always lower the total (each extracted helper is scored separately — `installCommand` first went 56 → 41 *plus* a new 16 before falling below the threshold), and cognitive complexity is the metric that tracks how hard code is to READ, so a cyclomatic-clean function can still be unreadable at 40+.
- **Raw lizard CCN is not comparable across versions, so the gate toolchain is pinned in `tools/gate-tools.json`.** `npm run verify:gate-tools` (also called by `npm run smoke`) compares that file against what is actually on PATH and fails on drift; `GATE_TOOLS_CONFIG` points it at another file. Three reasons the pin is load-bearing rather than ceremonial. **(1)** lizard's CHANGELOG 1.24.2 says counting `??`/`??=` and default parameters means *"existing scores may decrease"* and *"existing scores and threshold warnings may increase"* — one `pip install -U` moves every CCN at once, with no gate complaining. **(2)** A stale lizard is missing whole features: **1.24.1 added `-Ecognitive`** (`CogC` column, `--CogC N` defaulting to 15), so this machine's 1.21.3 answered `lizard --help` with no cognitive option and an earlier reading of this file wrongly recorded the metric as nonexistent. Minimum is therefore set to 1.24.1, and the verifier reports "older than the required minimum" separately from a plain pin mismatch. **(3)** Older lizard over-charges nested functions: `scripts/prune-runtime-deps.mjs#collectAppRoots` measured **53** on 1.21.3, **7** on 1.25.0, and **1** by TypeScript AST, because the old parser attributed the nested `walk`'s branches to the outer function. Upgrade it deliberately: bump the `pinned` value and keep the `why` text current — `tests/gate-tools-pin.test.ts` fails if a pin has no recorded reason, so the file cannot rot into a list of unexplained numbers. Measured 2026-11-03: lizard 1.25.0, semgrep 1.183.0, detect-secrets 1.5.52, all matching. **Even on 1.25.0 lizard still disagrees with the AST on 82.8% of functions (820 of 990, 817 of them inflated)** — `src/api/plans.ts#interviewPlanRoutes` is 145 for lizard and 1 by AST, because lizard charges every inlined route handler's branches to the registering function. That is a design choice upstream has not changed (#467 and #524 fixed missed functions and swallowed boundaries, not attribution), which is why `.ccn-baseline.json` stores AST numbers and `scripts/ccn-report.cjs` overrides lizard's column rather than trusting it. xp-gate #729 tracks the gate-side consequences.

- **`archlint-disable-next-line` does not work for `dead_code`, so entry points are ignored by exact filename.** `dead_code` flags a file that nothing imports, which is the DEFINITION of an entry point — `npm start` and the Dockerfile `CMD` both run `src/server-entry.ts`, and `.release-it.json` invokes `scripts/sync-version.cjs`. Rewritten to import the real `AnalysisService` and drive `calculateMetrics` / `compareClusters`, mutation-checked by doubling a scorer increment (2 tests fail). **The pattern to watch for is a test file with no `src/` import at all.**
- **ZERO production functions exceed 5, so Gate 3 is clean at its own threshold — but the 10-vs-5 trap is still live.** `npm run complexity` uses 10 while `adapters/gate-3.sh` defaults to 5, so "clean" depends entirely on which yardstick is named — always quote the threshold with the number. Measured at `572ac11` with `node scripts/ccn-report.cjs --threshold 5`: **0 production functions over 5**, and 41 under `tests/` which Gate 3 excludes via `CC_EXCLUDE`'s `(^|/)(tests?)/` and which are therefore not debt.   The lesson worth keeping from the cleanup is that **complexity debt was not where the bugs were — the untested guards were.** Every batch was mutation-checked, and 15 mutations that survived the suite marked genuine gaps rather than equivalent mutants. The pattern repeated in nearly every file: a guard existed, its happy path was tested, and the branch that exists to REFUSE something was not. Deleting `submitted.username !== expected.username` from the login route passed all 22 auth tests (every failure case submitted a wrong password, so bcrypt rejected regardless) — that one was an authentication hole, not a coverage nit. Others: a repeated `x-admin-key` header truncated to its first element; a plan with zero COMPLETED interviews being flipped to COMPLETED; `updatePlan` having no direct test at all, so both omitted-field and empty-date semantics were unguarded; a single interview tagging one dimension twice inflating a mention rate above 1.0; an Excel summary sheet asserted only by NAME, so truncating every finding to its first passed; a plan's `startedAt` reset on every resend; a message with no `messageId` silently dropped by the dedup cache. Measure the CCN, then mutate the refactor — the number going down proves nothing about protection.
- **`ccn-report.cjs --root` did not move the scan, and a missing root reported a clean tree — both fixed at `547c4c2`.** The flag only re-based the RELATIVE paths printed in the report; `DEFAULT_ROOTS` stayed relative to the CURRENT directory, so `--threshold 5 --root /other/checkout` measured THIS checkout and printed "No functions exceed the threshold". This was hit for real while re-verifying the 137: it came back **0**. Separately, `resolveFiles` wrapped `statSync` in try/catch and `continue`d, so a typo produced a clean tree with exit 0. Both are the failure the script's own header warns about — a clean verdict for a tree nothing read — and the second hid the first. Now relative roots resolve under `--root`, and an EXPLICITLY named root that does not exist exits **2** ("no evidence"), deliberately distinct from 1 ("debt found"). Default roots stay tolerant on purpose: `prisma/` or `scripts/` may legitimately not exist, and making those fatal fails 20 existing tests. **To measure another revision, either `--root <worktree>` (now correct) or pass absolute positional paths**; `git worktree add` plus a `node_modules` junction makes the old numbers reproducible without a second install. The regression test is worth copying: the first version ran with `cwd == --root`, so both interpretations produced identical output and it **passed against the bug** — pointing cwd and the root at different trees is what makes it a control.
- **`src/utils/startup-config-check.ts` was the last CCN-10 holdout.** It was the last holdout at CCN 15 — three independent areas (LLM key, DingTalk credentials, admin login) were checked inline in one function, so their branches accumulated into a single number. It is now a table of area-specific checks folded by `collectStartupConfigProblems`, which is a pure `flatMap` with CCN 1; the highest remaining piece is `checkDingTalk` at 4. Two things are worth keeping in mind before adding a check there: **(1)** each area returns `StartupConfigProblem[]` rather than pushing into a shared array, which is what makes it independently testable and lets the fold stay trivial; **(2)** `DINGTALK_REQUIRED` is a table of `{ variable, read }` rows precisely so a new required variable is a row instead of another `if`. The refactor was mutation-checked — deleting the `DINGTALK_AGENT_ID` row, disabling placeholder detection, forcing `checkAdminLogin` to return empty, and collapsing `firstSet` to a single lookup each fail at least one test — so the lower complexity did not cost any protection.
- **API bug triage**: curl → isolate backend first. htmx.ajax() `.then()` fires on 4xx with `undefined` arg.
- **A `[object Object]` in `Message.content` means a parser stringified a payload object, and the fix is extraction — never `String()` (issue #221).** DingTalk delivered a pasted/formatted reply as `{ msgtype: 'richText', content: { richText: [{ text: '…' }] } }`; `parseStreamMessage` read `data.text?.content ?? data.content`, got an object, and `String(object)` produced `"[object Object]"` — a **truthy, non-empty** string that passed the downstream `!content` and `!trim()` guards, was written to both `Message` and `Response`, and the interview advanced. Measured on a real v1.11.21 deployment: two user messages, length 15, `[object Object]`, questions 10 and 11 lost. `stream-message-utils.ts` now resolves text per message type (`text.content` → string `content` → joined `richText` text segments → `markdown.text`) and returns `''` for picture/voice/file bodies. **Two rules follow**: (1) never `String()` an untrusted JSON value into a text field — an object must degrade to `''`, so the existing empty-content guard rejects it; (2) a message with no text must be rejected by `processStreamMessage` (`Missing userId or content`), not silently dropped, or the user gets an LLM apology and loses the turn. Regression cover: `tests/stream-message-richtext.test.ts` (parser shapes, incl. an explicit "never `[object Object]`" sweep) plus three end-to-end cases in `tests/stream-message-service.test.ts`.
- **The admin tree leaf label is composed in the route, not the template (issue #223).** `tree-body.njk` used to render `interview.userId` alone, so an administrator read a column of numeric ids. The label is `姓名-电话-UserID` via `view-models.ts#interviewTreeLabel`, which needs the plan's `inviteeData` — so `findAllForAdminTree()` must select it. That select is the fragile link: dropping it again leaves the view-model unit tests green (they pass `inviteeData` directly) while the page silently regresses to bare ids. `tests/admin-tree-interview-label.test.ts` drives a real `GET /admin` for exactly that reason, and also asserts the imported name is HTML-escaped — it comes from a user-supplied CSV and lands in both element text and a `title` attribute.
- **Credential-free startup (issue #171)**: without `DINGTALK_CLIENT_ID`/`DINGTALK_CLIENT_SECRET`, `buildApp()` boots read-only (no Stream client). `runPostListenStartup` resends unsent messages only when all three DingTalk creds are set and `DISABLE_STARTUP_RESEND` (1/true/yes) is not set — startup outbound sends are a production side effect, never re-enable them unconditionally.
- **The gates run natively in Git Bash; `scripts/run-xp-gate-native.sh` is the entry point.** Every gate problem on this machine traced back to one line of environment: `bash` on the Windows PATH resolved to `C:\WINDOWS\system32\bash.exe`, which is the **WSL launcher**, not Git Bash. `core.hooksPath` points at a `#!/bin/bash` hook, so a `git commit` from Windows silently ran the whole suite inside WSL — a different filesystem, a different Python, and a different user's `~/.local/bin`. A `scripts/run-xp-gate.sh` wrapper used to exist to survive that jump (mount-translating `node` shims, `.exe` shims, a Windows `HOME`, `PYTHONUSERBASE`); it was deleted once PATH was fixed, because every workaround in it was compensating for a cross-environment hop nothing had asked to cross. Every tool the gates need is installed **natively on Windows** — node, git, gitleaks (scoop shim), `lizard` (`~/.local/bin`), `semgrep` (`~/bin`), `detect-secrets-hook` (`%APPDATA%\Python\Python312\Scripts`) — so with PATH ordered correctly (next bullet) the hooks run in Git Bash directly: one filesystem, one PATH, one Python, zero `/mnt/` paths. `scripts/run-xp-gate-native.sh` runs them explicitly and prints the resolved path of every tool first, so a wrong interpreter is visible in the first six lines instead of surfacing later as a mystery SKIP; `scripts/run-xp-gate-native.ps1` is the same from a PowerShell prompt. Measured: 10.0/10 effective with 9/12 gates actually executing (Gate 6 PASS, Gate 8 a real PASS from both scanners, Gate 10 PASS).
- **Development happens on Windows only; WSL is for running and deploying, not developing.** The project targets Linux in production (`DEPLOY.md`: any Linux box with Node 20.19+ and PostgreSQL 14+; Windows/macOS are dev-only), but nothing in this repo's development flow requires WSL — `scripts/deploy.sh`, the `Dockerfile`, `docker-compose.yml` and every CI workflow are WSL-agnostic, and the gates run entirely on Windows. A WSL worktree was tried and removed: it worked (167/167 files, 1967 tests, `tsc` clean, `biome check` clean on 284 files, 8/12 gates), but it duplicated a 663 MB dependency tree and needed manual syncing for an environment that gets little use. If someone does need to run the gates in WSL, they must use a checkout on the **Linux filesystem**, never `/mnt/*`: `/mnt/d` is one directory seen by two operating systems, so it carries a single `node_modules` holding only the native binaries of whichever platform last ran `npm install` — Windows writes `@biomejs/cli-win32-x64`, WSL needs `cli-linux-x64`, and Gate 1 then dies with `Cannot find module '@biomejs/cli-linux-x64/biome'` under `BLOCKED - Biome check failed`, which reads as a lint problem. Two further traps for that case: `~/.local/bin` (where the pip/tarball gate tools live) is added only by `~/.profile`, which non-interactive shells do not read, and the shared `core.git/config` `core.hooksPath` points at `C:/Users/think/.config/xp-gate/hooks` — a Windows path that does not exist in WSL, so a `git commit` there succeeds while silently skipping every gate.
- **PATH is ordered so `git commit` reaches Git Bash, and that ordering is load-bearing.** Windows concatenates the **machine** PATH row before the user row, so a user-PATH entry cannot outrank a machine entry — adding `C:\Program Files\Git\bin` to the user PATH did nothing while `C:\WINDOWS\system32` sat at machine index 5. `C:\Program Files\Git\bin` is therefore prepended to the **machine** PATH (index 0, ahead of `system32`), which is what makes a plain `git commit` run the hooks in Git Bash instead of the WSL launcher. Setting it needs admin rights (`Start-Process powershell -Verb RunAs`). Verify the ordering actually took effect by reading the registry, not `$env:PATH` — a running shell keeps the environment it was started with, so every child process inherits the *old* value and `where bash` keeps reporting `System32` until the shell is restarted:
  ```powershell
  (Get-Item 'HKLM:\SYSTEM\CurrentControlSet\Control\Session Manager\Environment').GetValue('Path', $null, 'DoNotExpandEnvironmentNames') -split ';' | Select-Object -First 3
  ```
  Do not "fix" the problem by deleting `system32\bash.exe` — `wsl` itself lives there, and `wsl` must keep working.
- **"Gate tool not installed" almost never means it is not installed.** `lizard` (Gate 3), `semgrep` (Gate 10) and `detect-secrets-hook` (Gate 8) are pip installs; they land in a *user* script directory, and two separate things hid them. First, the profile files that add that directory are read only by *interactive login* shells, so `command -v` in a non-interactive gate shell found nothing. Second — and this survives fixing the first — Python resolves user site-packages from `$HOME`, so under the old WSL wrapper, which repointed `HOME` at the Windows profile, a console script on PATH died with `ModuleNotFoundError: No module named 'semgrep'`. Both are handled now without any of that machinery: `scripts/run-xp-gate-native.sh` adds `~/.local/bin`, `~/bin` and the Windows Python `Scripts` dir to PATH, and Git Bash's `$HOME` already is the Windows profile, so `PYTHONUSERBASE` is unnecessary. Check the tool's own directory before installing anything — the versions natively installed here were in fact *newer* than the WSL ones.
- **Gate 5's local coverage judgement was inert (xp-gate #594), worked around in `vitest.config.ts`.** Gate 5 runs `vitest run --coverage <changed test files>`; when none of those tests imports a src module, istanbul writes `total.lines.pct = "Unknown"`, the hook does `Math.round("Unknown")` → `NaN`, and `[ NaN -lt 80 ]` makes bash print `integer expression expected` and return **2** — which `if` reads as "condition false", so it took the PASS branch and logged `NaN% ✅`. `coverage.include: ['src/**/*.ts']` + `cleanOnRerun: false` forces untested files into the report on a subset run too, so the total is always a real number. - **The full-history secret scan is a real gate again, via a fingerprint baseline (issue #211).** `scripts/scan-git-history-secrets.mjs` scans every commit (the `gitleaks-action` step only scans PR diffs, which is how two provider keys and a DingTalk app secret sat unreported for months). The CI step used to be `continue-on-error: true` so eleven known historical findings would not keep it permanently red — which also meant a NEW leak could never fail the build. `.secrets-history-baseline.json` now names each known finding by **fingerprint = sha256(rule + NUL + file + NUL + line), first 16 hex chars**, with a hand-written reason, and anything outside that list exits 1. Three rules keep the baseline from becoming the vulnerability it guards against: **(1)** an entry that matches nothing is itself a failure, so the file cannot rot into a wildcard; **(2)** matching is on rule+file+line, not file, so a new secret on another line of a historical file still fails; **(3)** the secret text is never stored — a baseline embedding the plaintext would be a second copy of the leak in a public repo. Regenerate only with `--write-baseline` **after** reading every finding; entries it cannot attribute are marked `NOT REVIEWED` and a test fails on that marker. The historical entries cannot be removed by rewriting history (pushed and cloned); they are acceptable because the DingTalk credentials belong to a virtual/test organization and both cloud keys are revoked.
- **A clean verdict from a scan that read nothing is the worst outcome, and there are now three guards against it.** `scan-git-history-secrets.mjs` exits 2 — never 0 — when gitleaks is missing, when `.gitleaks.toml` is absent, and when `git rev-list --all --count` is 0. The last one is not hypothetical: `gitleaks git` in a directory that is not a repository exits 0 with an empty report, so without the commit-count check the guard announced "history is clean" for a history it had never read. Same class of mistake as treating a missing scanner as a pass.

- **Gate 8 needs two things that look like one.** `adapters/gate-8.sh` gates the detect-secrets half on `command -v detect-secrets-hook && [ -f .secrets.baseline ]`, so with the tool present but no baseline it still prints "unavailable". `.secrets.baseline` is committed and `.gitleaks.toml` allowlists it — the baseline contains every pattern it found as literal text, which made gitleaks report 158 hits in it. `detect-secrets-hook` also rewrites line numbers in the baseline, so a Gate 8 block reading "Please `git add .secrets.baseline`" just means re-stage that file.

The scan *does* run (`INF scanned ~N bytes` / `INF no leaks found`); the gate simply has no evidence it can trust. xp-gate #592. - **The container deployment is now guarded by tests, and five of its defaults are load-bearing (issues #212–#218).** `tests/docker-compose-deployment.test.ts` (structure), `tests/docker-engine-consistency.test.ts` (Node version), `tests/lockfile-registry.test.ts` (lockfile hosts) and `tests/health-readiness.test.ts` (route semantics) fail if any of these is undone, so they read as constraints on every future change: **(1)** `package-lock.json` may only resolve from `registry.npmjs.org`/`yarnpkg.com` — `npm ci` fetches exactly the recorded URLs and `--registry` cannot override them for lockfileVersion 3, and `npm ci --package-lock-only` will NOT rewrite hosts on an otherwise-current lock (it prints "up to date" and exits 0), so a host fix is an explicit edit, not a regenerate. `.npmrc` selects the official registry; mirror acceleration is a per-machine setting. **(2)** `/health` is a LIVENESS probe (200 for `degraded`, 503 only when the DB is down) and `/health/ready` is the READINESS probe (200 only when everything works). Anything that waits for a working deployment — compose healthcheck, Dockerfile `HEALTHCHECK`, orchestrators — must poll `/health/ready`; both also parse the body, because `r.ok` alone made a deployment with no LLM key report `healthy` (#218). `start_period` is 60s because the first readiness probe awaits the 30s LLM timeout. **(3)** In `docker compose`, every `$` in a bcrypt hash must be written `$$` — `env_file` values are interpolated, so `$2b$12$…` reaches the container as `$2b$12` and the admin login 401s forever (measured). `docker run -e` does NOT interpolate, so the two paths need different literals from the same hash. `admin-auth.ts` now answers a malformed hash with 500 + an explicit message rather than a 401. **(4)** `POSTGRES_PASSWORD` is required via `${POSTGRES_PASSWORD:?…}` (no `change-me-in-env` default) and the postgres port is NOT published — the app uses `postgres:5432` internally, and a host mapping both collides with a local PostgreSQL and exposes the DB to the LAN (#215). **(5)** `REPORTS_DIR=/app/reports` is backed by the `reports_data` named volume; a bind mount hits the uid 1000-vs-1001 `nodejs` ownership trap, so the volume is the supported shape, and a backup covers **two** volumes (#216).
- **The CJK font is a Git LFS object, and the build now refuses to ship a pointer (#217).** `assets/fonts/*.otf` is LFS-tracked, so a clone without `git lfs pull` — CI without `lfs: true`, `git archive`, any scripted checkout — contains a 133-byte pointer that passes every "does the font exist" check. `scripts/verify-font-asset.mjs` validates the BYTES (LFS magic, OpenType/TrueType magic, size floor) in both Dockerfile stages; keep that RUN in the runner stage too, because that is the stage whose bytes actually ship. - **Node 22 is the floor, enforced in three places that must agree.** `Dockerfile` (`FROM node:22-slim` in both stages), `package.json` `engines`, and `.nvmrc` all say 22, because `@fastify/secure-session` → `@fastify/cookie` → `cookie@2` declares `engines.node: >=22`. `package.json` overrides `@fastify/cookie` to `11.1.0` — the last release on `cookie@1` — which deduplicates `cookie` to a single `>=18` entry; dropping that override reintroduces the EBADENGINE warning and the engine test fails on `node_modules/@fastify/cookie/node_modules/cookie`. - **The Docker image prunes build-time tooling, so it has no Prisma CLI (issue #210).** `Dockerfile` runs `scripts/prune-runtime-deps.mjs` between `npm run build` and the runner stage: `node_modules` 731 MB → 163 MB, image 1.22 GB → 574 MB. `npm prune --omit=dev` cannot do this — `prisma` and `typescript` are devDependencies AND optional peerDependencies of `@prisma/client`, so npm keeps them as `devOptional` and drags in Prisma Studio, `effect` and an embedded PGlite.
