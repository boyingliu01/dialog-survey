## 一、作品概述

**深访者**是一个 AI 驱动的异步多轮对话调研机器人。它通过钉钉与企业内部受访者进行一对一的文字对话，由大语言模型（LLM）实时判断"是否追问、如何追问、何时结束"，在受访者方便的时间完成一场有深度的访谈；访谈结束后自动产出结构化分析报告，并支持 PDF / Excel 导出与批量聚合分析。

三个关键词：

- **异步**：不要求访谈双方同时在线。机器人提问，受访者按自己的节奏回复，适配真实工作场景。
- **多轮深访**：不是一次性的问答，而是围绕每个话题最多进行 5 轮 LLM 智能追问的深度对话——这是与"问卷"的本质区别。
- **AI 原生**：追问决策、报告生成、维度标注、主题聚类全部由 LLM 驱动；访谈主持人"会追问、会共情、会收尾"的判断能力来自大模型。

一套完整的访谈生命周期：**模板设计 → 访谈计划 → 钉钉邀约 → 多轮对话 → 分析报告 → 导出/聚合**。

## 二、要解决的问题

企业内部调研长期存在两难：

| 方式 | 优势 | 致命短板 |
|------|------|----------|
| 传统问卷 | 覆盖面广、成本低 | 只能按脚本问封闭题，"背后为什么"深不下去 |
| 人工访谈 | 能追问、有温度、问得深 | 单人一天只能访谈几人，规模化成本极高 |

而现有"AI 问卷"类工具普遍缺三样东西，导致不可用于严肃调研：

1. **没有对话状态**——问完一轮就丢上下文，无法承接追问；
2. **没有追问能力**——只能按脚本顺序走，无法根据回答深挖细节；
3. **没有工程可靠性**——消息重复/丢失、LLM 输出失控（一次问多个问题）、并发写坏数据，调研数据质量无法保证。

**深访者的解法：把"访谈主持人的判断"交给 LLM，把"可靠性"交给工程。** 前者是 LLM 最擅长的（理解语义、判断情绪、决定追问方向），后者是软件工程最擅长的（状态机、乐观锁、幂等、降级）。两者结合，才能让"深访"这件事既保持质量、又可规模化。

## 三、整体方案设计

### 3.1 系统架构

工程采用严格的分层架构（由 `architecture.yaml` 声明并被 CI 校验依赖方向）：

```
┌─────────────────────────────────────────────────────────┐
│  api/            Fastify 路由层（HTTP API + Admin UI）       │
│    ↓ 只能依赖 services / integrations                        │
├─────────────────────────────────────────────────────────┤
│  services/       业务编排层（18 个服务）                      │
│    ↓ 只能依赖 repositories / core / integrations              │
├──────────────────────────┬──────────────────────────────┤
│  core/  对话引擎（自研状态机）  │  integrations/ 钉钉 + LLM     │
│    ↓ 只能依赖 repositories    │   （Stream 长连接 / OpenAI 兼容）│
├──────────────────────────┴──────────────────────────────┤
│  repositories/   Prisma 数据访问层（乐观锁持久化）              │
├─────────────────────────────────────────────────────────┤
│  PostgreSQL 16   （10 张数据表）                             │
└─────────────────────────────────────────────────────────┘
        utils/  横切工具层（日志/安全/重试/PII，零内部依赖）
```

分层依赖方向由机器校验：`api → services → repositories`，反向依赖会在 CI 中失败。这保证任何一层都可以被独立测试和替换。

### 3.2 技术选型

| 层面 | 选型 | 说明 |
|------|------|------|
| 语言 | TypeScript（strict，ESM） | 全量类型覆盖，无显式 any |
| Web 框架 | Fastify 5 | 高性能、schema 校验、插件化 |
| 数据库 | PostgreSQL 16 + Prisma 7.10 | 事务 + 乐观锁并发控制；集成测试内嵌 PGlite（免真实 DB 依赖） |
| 对话引擎 | **自研确定性状态机** | 见 4.1 节"为什么不用现成图框架" |
| LLM 接入 | OpenAI 兼容接口 | 云端/本地模型通吃（可接 Ollama 等） |
| 消息通道 | 钉钉 Stream 模式（WebSocket） | 免公网 IP、免回调服务器 |
| 管理界面 | Nunjucks + HTMX + Alpine.js | 轻前端，服务端渲染 |
| 测试 | Vitest 4 + Playwright | 单元/集成/E2E 三层 |
| 质量工具链 | Biome + tsc + ast-grep + semgrep + gitleaks + Stryker | 见第五章 |

### 3.3 一次访谈的完整生命周期

```
① 管理员在 Admin UI 创建访谈模板（话题脚本 + 结构化维度 JSON）
        ↓
② 创建访谈计划，导入受访者名单（Excel/CSV，自动匹配钉钉用户）
        ↓
③ 系统经钉钉向受访者发送访谈邀请
        ↓
④ 受访者回复后进入对话：首问 → LLM 逐题判断「追问 / 推进 / 结束」
   （每题最多 5 轮追问，全程带 6 条对话历史上下文）
        ↓
⑤ 访谈完成 → 系统自动异步触发分析管线（维度标注 + 报告生成）
        ↓
⑥ 管理员查看结构化报告（关键发现 / 情感分析 / 行动建议 / 维度引用）
        ↓
⑦ 单份导出 PDF / Excel；多份批量聚合为整体洞察报告
```

## 四、核心技术与实现亮点

### 4.1 对话引擎：确定性状态机（自研，非框架拼装）

对话引擎是整个系统的心脏，也是工程判断最集中的地方。**我们没有引入 LangGraph 的 StateGraph API，而是自研了一个 86 行入口 + 204 行节点的确定性状态机**，理由如下（该决策有专门的设计评估文档记录）：

- 本项目的对话流程是**两个节点的线性状态机**（planning → interviewing），核心复杂度不在"图编排"，而在状态一致性、并发控制、降级容错——这些是框架解决不了的问题；
- 引入图框架意味着 4-8 周迁移成本，收益仅为少量 API 便利，**投入产出比不成立**；
- 自研使状态流转完全可解释、可测试：**5 条路由规则**覆盖了所有真实的对话分支。

**状态定义**：访谈实例的 6 种状态（PENDING / ACTIVE / PROCESSING / WAITING / COMPLETED / CANCELLED）由 zod schema 严格定义，并携带乐观锁版本字段。

**路由规则**（`interviewing` 节点决策表）：

| 规则 | 触发条件 | 动作 |
|------|---------|------|
| Rule 1 | LLM 请求追问，但已达追问上限（默认 5 次） | **强制推进**到下一题，防止无限追问 |
| Rule 2 | 用户明确要求结束 | 直接完结访谈 |
| Rule 3 | LLM 判定 FOLLOWUP | 追问计数 +1，留在当前话题 |
| Rule 4 | 其他停留类响应 | 同样计数（防"无进展死循环"） |
| Rule 5 | LLM 判定 NEXT | 推进到下一题；已是最后一题则完结 |

> 设计要义：**LLM 拥有"建议权"，规则引擎保留"否决权"**。Rule 1 / Rule 4 就是兜底护栏——无论 LLM 如何输出，访谈一定会在有限轮次内收敛。

**降级设计**：当 LLM 调用失败时，引擎返回预置降级响应推进对话，保证访谈不中断（好于"卡死"）。

**完访谈收尾**：访谈完结时通过 `setImmediate` 异步触发分析任务，**不阻塞用户的最后一条消息响应**。

### 4.2 LLM 智能追问：让模型"会聊天"，让工程"不出格"

追问质量是访谈深度的直接来源。`followup` 服务把"如何回应受访者"的决策完整交给 LLM，同时用工程手段约束其输出：

**① 结构化决策输出**：LLM 不是直接吐一段话，而是返回结构化 JSON——包含思考过程（thinking）、所选策略（strategy）、行动决策（action）、回复内容（response）。程序只执行 action，不解析自然语言判断。

**② 9 种应对策略**（覆盖访谈中的真实情况）：

| # | 策略 | 场景 |
|---|------|------|
| 1 | 认真回答 | 肯定并深入挖掘细节（具体场景、亲身经历、个人建议） |
| 2 | 敷衍回答 | 先回应情绪，再换角度激发兴趣 |
| 3 | 困惑不理解 | 解释话题含义，温柔引导 |
| 4 | 拒绝不想答 | 表示理解，进入下一题 |
| 5 | 不满情绪激动 | 真诚道歉共情，尊重选择 |
| 6 | 要求结束 | 确认结束，感谢并祝福 |
| 7 | 要求跳过 | 同意跳过，直接下一题 |
| 8 | 质疑测试边界 | 温和重申角色，保持专业 |
| 9 | 转移话题 | 温和引导回主题或接受转移 |

**③ 提示词工程护栏**（这些细节决定了访谈质量的上下限）：

- **单问题铁律**：提示词中标识为最高优先级规则——"每次回复只能包含一个问题"，并附正反示例；程序侧对回复做**问号计数自检**，多问即打回；
- **禁止提前铺垫下一题**：追问阶段不得暗示、铺垫下一话题，避免污染当前话题的深挖；
- **深度追问引导**：明确要求模型追"具体场景"而非抽象概念、追"亲身经历"而非泛泛而谈、追"个人真实想法"而非官方回答；
- **上下文窗口**：注入最近 6 条对话历史，让模型理解对话脉络；
- **注入防护**：所有模板变量替换时对 `{{` 做转义，防止受访者输入构造模板注入；
- **超限兜底**：追问次数达到上限时，程序强制切换为推进动作，不依赖模型自觉。

**④ 失败降级**：LLM 调用异常时返回预置降级话术，附独立重试机制（指数退避），保证端到端对话永不卡死。

### 4.3 状态持久化：乐观锁 + 两阶段提交

异步对话场景下，同一个用户的消息可能并发到达或重复投递，状态写坏的代价是**访谈数据污染**。为此数据层做了三层防护：

**① 乐观锁**：每个访谈状态带 `version`（当前版本）与 `originalVersion`（加载时版本）两个字段。写入时校验版本一致才落库，不一致抛出版本冲突，由上层重试（最多 3 次）。选择乐观锁而非悲观行锁的原因：对话处理链路长（含 LLM 调用），持锁等待会显著降低并发吞吐。

**② 两阶段提交**：LLM 调用属于外部慢操作。我们把一次消息处理拆成两段持久化——

```
加载状态 → 先落 PROCESSING（记录"正在处理"） → 调用 LLM → 落最终状态
                    ↑                                    ↑
             崩溃/宕机时：消息不会丢，状态可追溯       失败时进入死信告警
```

**③ 增量写入**：状态保存时只对新增消息/回答执行批量插入（`createMany`），而非全量重写，避免长时间事务与写放大。

**错误分类**：数据层定义了专门的持久化异常类型（版本冲突 / 事务错误 / 记录不存在），让上层可以按错误类别做出不同处置（重试 / 告警 / 忽略），而不是笼统 try-catch。

### 4.4 消息处理管线：面向生产环境的可靠性设计

钉钉消息入口是系统与外部世界的第一道闸门，这里集中了六项可靠性设计：

| 机制 | 实现 | 解决的问题 |
|------|------|-----------|
| **消息去重** | LRU 缓存（容量 1000）记录已处理消息 ID | 钉钉消息重复投递导致重复处理 |
| **用户级互斥锁** | 同一用户的消息串行处理，后到者排队 | 用户连发多条消息导致状态并发写冲突 |
| **对话冷却守卫** | 30 分钟无互动不再主动打扰 | 避免"机器人骚扰感"，保护用户体验 |
| **超时 nudge** | 访谈挂起 1 小时后温和提醒，最多 3 次 | 受访者忘记回复导致访谈烂尾 |
| **死信告警** | 处理失败的请求落入死信记录并告警 | 线上问题可发现、可追溯、可补救 |
| **SSRF 防护** | Webhook 目标域名白名单（仅钉钉官方域名） | 恶意请求诱导服务端访问内网 |

**幂等分析**：访谈完结触发的分析任务先删除旧报告再生成新报告，天然幂等——重跑不会产生重复报告。

### 4.5 分析管线：从对话记录到决策洞察

分析管线是"把访谈变成结论"的关键环节，设计为**双轨并行**：

**① 通用报告轨**（每份访谈一份）：
- 生成结构化报告：访谈概述 / 关键发现（附受访者原话引用）/ 情感分析 / 痛点与需求 / 行动建议（带优先级）/ 亮点引用；
- 输出格式兼容 Markdown 与纯文本两种解析路径，解析失败自动降级为**兜底报告**（原始问答记录），保证"报告永不缺失"；
- **PII 匿名化**：引用分析前对手机号（138\*\*\*\*1234）、邮箱、人名做匿名化处理，隐私数据不进入报告。

**② 维度分析轨**（面向结构化洞察）：
- 模板可预置**结构化维度 JSON**（如"响应速度 / 产品功能 / 服务态度"等自定义维度）；
- LLM 按维度对回答做标注：维度标签 + 情感倾向 + 原文引用 + 涌现标签（预设维度之外的新发现）+ 访谈员评分；
- 低温度采样（0.1）保证标注结果可复现。

**③ LLM 主题聚类**：对一批访谈自动归纳 3-8 个子主题，并提炼 Top 5 涌现议题（带紧迫度分级）——让"读了 50 份访谈"变成"读了 1 页结论"。

**④ 批量聚合引擎**（面向多份访谈）：
- **Checkpoint 断点续跑**：聚合任务中途失败可从中断处继续，不重头再来；
- **并发限流**：通过 p-limit 控制 LLM 调用并发，避免打爆 API 配额；
- **超时保护**：单批聚合 5 分钟超时上限，防止挂起任务占用资源；
- 维度统计输出提及率与情感分布。

### 4.6 报告导出与交付

- **PDF 导出**：Playwright 无头浏览器渲染 A4 报告（含受访者信息、问答记录、分析报告），支持自定义 Chromium 路径以适配受限环境；
- **Excel 导出**：问答明细 + 报告结论多 Sheet 输出，便于二次分析；
- **Admin UI**：基于 Nunjucks + HTMX 的管理界面，覆盖模板管理、计划管理、成员管理、报告查看、统计分析全流程；登录态采用 secure-session + CSRF 保护 + 登录限流（5 次/15 分钟）。

## 五、工程质量保障

**"代码之美"不止是功能跑通，更在于代码长期可维护、可信任。** 本项目把质量保障做成了基础设施：

### 5.1 测试体系

| 层次 | 范围 | 现状 |
|------|------|------|
| 单元测试 | 服务/工具/节点（mock 数据层） | 主体，139 个测试文件 / 1,400+ 用例 |
| 集成测试 | 内嵌 PGlite 全链路（无需外部数据库） | 状态持久化、模板 CRUD、导出等 |
| E2E 测试 | Playwright 管理界面全流程 | Admin UI 关键路径 |

### 5.2 覆盖率与质量门禁

- 覆盖率门槛 **80/70/80/80**（statements/branches/functions/lines），由 `vitest.config.ts` 强制，**不达标 CI 直接失败**；
- 最近一次完整质量门禁报告（2026-06-12）：statement 83.32% / branch 70.87% / function 87.16% / line 82.82%，全部达标；
- 内置质量门禁工具链（XP-Gate）：代码质量、重复代码（jscpd）、圈复杂度（lizard）、架构分层、变异测试等多维检查报告；
- 采用 **Delphi 多专家评审法**对设计方案做独立交叉评审后才进入编码。

### 5.3 CI 流水线（11 个 Job，PR 必过）

| Job | 内容 |
|-----|------|
| Static Analysis | Biome（lint + 格式 + import 规范）+ tsc 类型检查 + ast-grep 自定义架构规则 |
| Unit Tests | 全量单元测试（内嵌 PGlite，无需外部数据库） |
| Integration Tests | 集成测试（内嵌 PGlite + 环境变量注入） |
| E2E Tests | Playwright 管理界面端到端测试（内嵌 Fastify + 真实 Chromium） |
| Backup Drill | **备份恢复演练自动化**：定期验证备份可真实恢复，防"备份在手、恢复无门" |
| Security Scan | semgrep SAST 扫描 + gitleaks 密钥扫描 |
| Coverage | 全量覆盖率校验（阈值强制） |
| Mutation Tests | Stryker 变异测试（验证测试用例的真实有效性） |
| Smoke | 类型 + 规范 + 核心冒烟用例快速验证 |
| Commit Lint | 提交信息规范校验 |
| Version Consistency | 多文件版本号一致性校验 |

此外还有独立于 PR 流水线的 **月度负载测试流水线**（见 5.6 节）。

### 5.5 静态质量规则（写入配置、机器强制）

- TypeScript strict 模式 + ESM；禁止显式 `any`；
- Biome 规则：禁止 `forEach`（统一 for...of）、禁止 `console`（统一结构化日志）、强制 `import type`；
- **自定义架构规则（ast-grep）**：禁止 API 层直接使用 Prisma 原生调用，数据访问必须走 repositories 层；
- 分层依赖方向由 `architecture.yaml` + 架构基线校验守护。

### 5.6 性能与容量验证（v1.11.0 新增）

性能不是拍脑袋估的——本项目自建了**可重复执行的负载测试基线体系**：

- **自研 harness**：autocannon 驱动 6 个场景（S1 静态 / S2 简单 API / S3 复杂查询 / S4 批量导入 / S5 报告导出 / S6 对话全链路），真预热 5 秒、直方图 p95 插值、try/finally 资源保障、测量期凭据双重剥离（防 LLM 外呼污染基线）；
- **真实 PostgreSQL 权威数字**（2026-10-09 CI 实测）：S4 批量导入 ~1,095 rps、S5 报告导出 ~1,024 rps、S6 对话全链路 ~139 calls/s（tier-200 配置，30 分钟 0 错误 0 非 2xx）；
- **月度 CI 复测防回归**：负载测试流水线每月 1 号自动执行，结果 JSON 自动归档到专用 baseline 分支，与基线对比即可发现性能退化；
- **容量规划落地**：`DEPLOY.md` 据此给出部署容量建议（单进程对话处理 ~30-50 calls/s、并发上限 50），并明确标注"未校准本地估算"与"实测数字"的边界——数字来源诚实可查。

> 方法论注记：v1 基线曾因对话场景大量命中冷却早退路径而虚高 10 倍，v2 重写后修复并留档（报告 §4.8）——测量本身的陷阱也被文档化了。

### 6.3 安全设计

- API Key 全部以 SHA-256 哈希存储，校验使用**时间安全比较**（防时序攻击）；
- 登录限流 + 审计日志 + CSRF 保护 + secure-session；
- 敏感信息（PII）在分析链路上做匿名化处理；
- 密钥扫描（gitleaks）纳入 CI，防密钥泄漏入库。
