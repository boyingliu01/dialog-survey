## 三、本周期主要成果

### 3.1 生产镜像：从"无法启动"到可用（issue #210）

这是本周期最重要的发现。镜像体积问题只是表象，**真正的问题是它从来没能启动过**。

**时间线**（来自 git 记录）：

| 日期 | 事件 | 状态 |
|---|---|---|
| 2026-03-12 | 引入 Docker（`python:3.11-slim`） | — |
| 2026-06-16 | 改用 `node:20-alpine` | 当时可启动 |
| **2026-07-15** | 引入 `@fastify/secure-session` | ❌ **从此无法启动** |
| 2026-10-27 | 改为 `node:20-slim` | ✅ 恢复 |

**根因**：`@fastify/secure-session@8` → `sodium-native@5.1.0`，后者没有 `install` 脚本（不现场编译），`prebuilds/` 只有 `linux-x64`/`linux-arm64`（glibc），**没有 `linux-x64-musl`**。Alpine 是 musl，必然在启动时崩溃。

**为什么 3.5 个月没人发现**：`DEPLOY.md` 从未写过 Docker 部署模式，CI 也没有构建镜像的作业。**没有真的跑过它**。

**成果**：

| 指标 | 修改前 | 修改后 |
|---|---|---|
| 镜像 | 1.22 GB | **574 MB** |
| `node_modules` | 731 MB | 163 MB |
| 包数 | 588 | 148 |

`npm prune --omit=dev` 做不到这一点：`prisma` 和 `typescript` 既是 devDependencies 又是 `@prisma/client` 的 optional peerDependencies，npm 会记为 `devOptional` 保留下来。改用已有的 `scripts/prune-runtime-deps.mjs`（从 `dist/` 的实际 import 推导依赖图）。

### 3.2 迁移方案：没有 Prisma CLI 也能迁移

prune 移除了 `CMD` 依赖的 Prisma CLI，故新增 `scripts/migrate-deploy.mjs`：用 `pg` 执行 `prisma/migrations/*.sql`，并按 **Prisma 官方格式**（同 SHA-256 checksum）写入 `_prisma_migrations`。

**双向互换已实测**：

| 场景 | 结果 |
|---|---|
| 本脚本迁移 → `prisma migrate deploy` | `No pending migrations to apply` ✅ |
| CLI 迁移 → 本脚本 | `up to date` ✅ |

因此 `deploy.sh` 与容器可管理同一数据库，不会重复执行（迁移 SQL 非幂等）。

### 3.3 两个启动期缺陷

- **`pino-pretty` 是 devDependency**：prune 后不设 `NODE_ENV=production` 会崩溃（`unable to determine transport target for "pino-pretty"`）。`createLoggerConfig` 现在在包不可解析时降级为纯 JSON。
- **`SESSION_SALT` 必须是 32 个 hex 字符**：`Buffer.from(salt, 'hex')` + secure-session 的 16 字节要求。16 个任意字符会报误导性的 `salt must be length 16`。

### 3.4 管理界面不再依赖 CDN 加载 htmx

两个布局原本用 `https://unpkg.com/...` + `onerror` 回退。**这个回退不可靠**：`onerror` 只在请求彻底失败时触发，网络慢的时候不触发，脚本半加载后 `htmx` 永远是 undefined，页面却照常渲染。

`public/js/htmx.min.js`（82 KB）早就存在却只在错误路径用。已改为直接加载本地文件，Alpine 同样处理。

**验证**（证明是既存缺陷）：

| 版本 | 全量测试 |
|---|---|
| `799e456`（改动前） | 2 failed / 1963 passed |
| `60b1340`（改动后） | **1965 passed** |

Tailwind 仍走 CDN——它是运行时编译器，模板用到的工具类需要它生成，无法简单换静态文件。这是管理界面最后一个网络依赖。

### 3.5 研发云材料保全

研发云仓库与本地已分叉（共同祖先停在 2026-03-12），因为之前的同步是「snapshot sync」整树覆盖而非正常推送。

## 五、环境配置（本机）

### 5.1 必须保持的配置

**PATH 顺序是承重的**：`C:\Program Files\Git\bin` 被前置到 **machine** PATH（索引 0，在 `system32` 之前）。这决定了 `git commit` 的钩子跑在 Git Bash 里而不是 WSL 启动器。

Windows 会把 machine PATH 排在 user PATH 之前，所以**加到 user PATH 没用**。修改需要管理员权限。验证要看注册表，不能看 `$env:PATH`（运行中的 shell 保留启动时的环境）：

```powershell
(Get-Item 'HKLM:\SYSTEM\CurrentControlSet\Control\Session Manager\Environment').GetValue('Path', $null, 'DoNotExpandEnvironmentNames') -split ';' | Select-Object -First 3
```

**开发只在 Windows 上进行**，WSL 用于运行和部署。WSL 的工作树已删除（重复占用 663 MB 依赖树，且几乎不用）。

### 5.2 本周期修复的环境问题

**checkov 的 shebang 带空格未加引号**：

```
#!C:\Program Files\Python312\python.exe    ← 在 Git Bash 下被截断成 "C:\Program"
```

已改为 `#!/usr/bin/env python`（文件：`%APPDATA%\Python\Python312\Scripts\checkov`）。修复后 checkov 3.3.30 可用，Gate 7 通过。

这不是仓库配置，重装 Python 或 checkov 后可能复发。

### 5.3 门禁运行方式

```bash
bash scripts/run-xp-gate-native.sh pre-commit
```

入口脚本会先打印每个工具的解析路径，所以路径错误在前六行就能看出来，不会拖到后面变成神秘的 SKIP。

## 六、已知遗留问题（不阻塞归档）

### 6.1 研发云 Gitea TLS 缺陷（已转交平台团队）

`openresty/1.19.3.1` + Gitea 1.22.1 在返回大响应时，关闭连接前不发送 TLS `close_notify`。

- 小响应（4 KB）正常；大响应（17 MB）必现 `curl 56 ... missing close_notify`
- **数据本身完整**：`git index-pack` 校验通过
- 客户端行为正确（TLS 无法区分"说完了"和"被截断"）

**报告**：`docs/dt-gitea-tls-defect-2026-10.md`

**最危险的现象是 push「假失败」**——服务端已接受提交，客户端仍报错。这会诱导重复推送或 `--force`，进而丢历史。研发云上那些 `snapshot sync` 全树覆盖提交正是这样产生的。

> ⚠️ 平台修复前，向研发云推送后**必须用 `git ls-remote dt master` 核对 SHA**，不要因报错就重复推送。

**2026-11 跟进**：研发云团队给出的方案（`git config --global http.sslBackend openssl`）已实测**无效**——schannel/openssl、TLS 1.2/1.3、HTTP/1.0、shallow fetch 全部复现，缺陷在服务端 openresty 收尾。当前环境状态与操作规范见该报告 §11：推研发云统一用 `tools/push-dt.ps1.example`（复制到 scripts/ 下即可使用，自动核对 SHA），日常以单向推送为主，从 dt fetch 暂不可行。

### 6.2 本地门禁的 E2E 偶发超时

本地跑全量测试时，偶尔有一个 E2E 文件报 `page.goto: Timeout 30000ms`。

**已确认非代码问题**：

| 场景 | 结果 |
|---|---|
| 全量混跑（12 个 E2E 与 1900 个单元测试共享 4 个 worker） | ❌ 随机失败，每次命中的文件不同 |
| 单独跑 E2E | ✅ 12 文件 / 87 测试全通过 |
| 降到 2 worker 混跑 | ❌ 仍失败 |

根因：每个 E2E 文件独立 `chromium.launch()`，与 PGlite 单元测试争抢同一资源池。

**CI 不受影响**，因为它把测试分成 4 个独立 job。

**建议的修复**（未实施，属于新增特性）：为 E2E 单独配 Vitest project 并设 `fileParallelism: false`，或在门禁中分段执行。

用户已停用（欠费）。这带来一个认知：本仓库目前是「**本地门禁把关 + 手工分段验证**」模式。

## 七、给后续维护者的三条硬性约束

这三条都已写入 `AGENTS.md`：

1. **Docker 必须用 Debian slim，不能回 Alpine**
   `sodium-native` 没有 musl 预编译件，镜像会在启动时崩溃。

2. **`SESSION_SALT` 必须是 32 个 hex 字符**
   `Buffer.from(salt, 'hex')` + secure-session 要求 16 字节。16 个任意字符报的错是 `salt must be length 16`——数字看着对，实际是编码问题。

3. **镜像内没有 Prisma CLI**
   迁移由 `scripts/migrate-deploy.mjs` 执行，已与官方 CLI 双向验证可互换。不要试图在容器里调用 `node_modules/prisma/build/index.js`。
